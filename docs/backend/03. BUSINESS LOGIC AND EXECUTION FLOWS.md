# Business Logic and Execution Flows

## 1. Standard research query

Primary implementation: `research()` and `_research_impl()` in
[`app/routes/research.py`](../../app/routes/research.py#L160).

1. FastAPI validates `ResearchRequest`; `resolved_query()` chooses `query`
   before `text` and rejects an empty request with HTTP 400.
2. `research()` wraps `_research_impl()` in `asyncio.wait_for()` using
   `REQUEST_TIMEOUT`. Timeout returns HTTP 504.
3. `_research_impl()` checks `pool.assert_ready()`, runs the process-local IP
   rate limit, sets optional user context, obtains the user's plan, clamps
   `top_k`/heavy features for free users, and calls the credit helper.
4. It checks special modes first: PDF URL/link, uploaded PDF, then Wikipedia
   prefix/mode. These paths can return without entering general paper
   retrieval.
5. General requests call `plan_query(query, conversation_context)`. Planner
   output is normalized into a `QueryPlan`; planner exceptions fall back to a
   keyword-based `rag` plan.
6. Route-specific shortcuts handle `chitchat`, `context_only`,
   `entity_lookup`, `structured`, and `title_lookup`. Routes needing evidence
   proceed to parallel graph/vector and provider retrieval.
7. Retrieved papers are relevance-filtered and ranked. Metadata may be
   enriched from Semantic Scholar and Papers With Code/Hugging Face. Datasets
   and repositories are assembled by utility functions; Kaggle enrichment is
   attempted only when datasets already exist.
8. For high-depth RAG/compare plans, up to three named primary papers can be
   fetched as PDFs and searched for matching passages. Fetch/extract failures
   do not stop the rest of the response.
9. The selected prompt is sent to Groq. High-depth answers receive a
   requirements coverage check. Optional answer verification runs only if
   evidence exists and request `verify` is true.
10. Citation links are cleaned/resolved and the response includes answer,
    route/plan metadata, evidence arrays, datasets/repos, verification,
    elapsed time, model, warning, and credit snapshot.

### Standard no-evidence behavior

If chunks, graph nodes, external papers, and PDF context are all empty, the
route returns a fixed “couldn't retrieve research sources” answer without
calling the answer-generation model. It includes empty evidence and resource
arrays, `verification: null`, `model_used: null`, and a warning. This is a
normal JSON response rather than an HTTP error.

## 2. Chat and follow-up

`POST /api/chat` accepts conversation messages, resolves the latest user
message and a compact context from recent turns, then uses the planner to
classify the follow-up. Context-only requests can use prior conversation
content without performing new retrieval. Other routes fan out to graph,
vector, ArXiv, Semantic Scholar, and repository/dataset enrichment similarly
to the research path. The endpoint returns assistant output and source
metadata; it does not persist the conversation automatically in the
`chat_sessions` collection in every path. The separate history endpoints
provide explicit session persistence.

The OpenAI-compatible `POST /v1/chat/completions` is a distinct wrapper: it
requires Pro, uses the request's messages directly, calls Groq, and returns a
Chat Completions-shaped non-streaming response.

## 3. User registration and login

1. `POST /api/auth/signup` lowercases/strips email, performs a basic address
   check, checks duplicate email, and hashes the password with bcrypt.
2. When email verification is disabled (the default), a user is inserted as
   verified and the endpoint returns success without sending email.
3. When enabled, it creates a code/expiry, calls the configured email helper,
   and stores pending verification data.
4. `POST /api/auth/login` retrieves by normalized email and checks the bcrypt
   hash. If verification is enabled, unverified accounts are rejected.
5. Successful login signs a JWT with subject, email, and expiry; API clients
   send it as `Authorization: Bearer <token>`.
6. Protected routes decode the token and re-read the MongoDB user; token
   presence alone does not bypass the user lookup.

MongoDB stores passwords as hashes, not plaintext. Password policy is a
minimum length of six characters; no stronger composition rule is visible in
the request model.

## 4. Uploaded PDF and PDF question answering

1. `POST /api/upload/pdf` checks filename extension and configured byte limit,
   extracts document text using PyMuPDF in a worker thread, applies the
   internal text cap, and stores `{_id, name, text, uploaded_at}` in
   `uploaded_pdfs`.
2. The response returns a PDF API URL containing the new ID. The frontend can
   use that URL later as context.
3. Research recognizes a local `/api/pdf/{id}` link and loads stored text.
   Remote ArXiv abstract links are converted to PDF URLs; PDFs are downloaded
   with size checks and parsed for text and external links.
4. PDF question answering chunks document text, computes query/document
   embeddings with retrieval freeze bypassed, ranks with cosine similarity,
   and sends selected passages into a grounded prompt.
5. Upstash Redis is used for compressed chunk/embedding cache when configured;
   in-memory caches are the fallback.

Uploaded file retrieval is by ID; the visible `uploaded_pdfs` record does not
include an owner ID and the GET endpoint does not visibly perform an ownership
check. See the security guide.

## 5. Timeline and survey

`/api/research/timeline` and `/api/research/survey` have dedicated request
models/prompts. Both gather graph/vector results and external research
sources; the database retrieval pieces yield no results when frozen.
Timeline builds chronological evidence and calls the heavy model. Survey uses
the survey prompt, always selects the heavy model, and may query graph
co-citation helpers. Survey is Pro-gated; timeline is not visibly gated by
plan beyond rate/credit helper behavior.

## 6. Bulk research

`POST /api/research/bulk` is Pro-gated and accepts 1–10 queries. A semaphore
limits concurrent `_research_impl()` calls in this process to three. Each
item is independently wrapped; an exception becomes an item-level error
instead of aborting the whole batch. The route returns all item results.

## 7. Citation comparison

`POST /api/graph/compare` resolves two paper references through graph lookup
and ArXiv search, retrieves optional chunk evidence, constructs a comparison
prompt, calls Groq, and returns comparison answer plus retrieved records.
Graph lookups may be empty when retrieval is frozen. It is not marked Pro-only
in the route source; it calls the credit helper, which is inactive when credit
enforcement is disabled.

## 8. Sources and Datasets UI data

Research response assembly includes both papers and dataset/repository
metadata. Dataset lookup is a follow-on enrichment step, not a guarantee that
a dataset was available for every paper or query. The frontend Sources panel
renders returned dataset cards; the empty state means the API returned no
datasets, not necessarily that no academic papers were retrieved.

## 9. Payment and plan updates

- Razorpay order creation uses configured credentials and stores payment
  transaction records when the handler receives a user context supported by
  the implementation.
- Razorpay verification checks a server-side HMAC signature before setting
  the user's plan to Pro.
- Stripe plan changes are processed by `/api/auth/upgrade`; a webhook secret
  is checked when configured, after which checkout/subscription events update
  the plan.
- Credit accounting is feature-flagged off by default. Some Pro feature gates
  remain active even while the credit limit is frozen.

## 10. Separate graph-service workflow

The `knowledge_graph/` package offers its own Neo4j driver, sample seed data,
schema setup, graph query functions, and FastAPI app. It is not an ingestion
orchestration feature of the main request path and does not become active just
because `knowledge_graph/api.py` exists. The main app has a separate graph
adapter in `app/core/graph.py`, and that adapter respects
`FREEZE_RETRIEVAL`.
