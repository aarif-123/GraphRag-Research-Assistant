# Error Handling and Reliability

## Error categories and API behavior

| Failure | Typical handling |
|---|---|
| Invalid Pydantic input / required fields | FastAPI validation response; query resolution may explicitly return HTTP 400 |
| Missing bearer token on protected route | HTTP 401 |
| Pro feature on free plan | HTTP 403 with `pro_required` detail |
| Exhausted credits when enabled | HTTP 402 with reset time and upgrade URL |
| Request rate exceeded | HTTP 429 |
| Top-level research/chat timeout | HTTP 504 |
| Groq generation failure | `LLMError` generally becomes HTTP 502 |
| PDF parse/download failure | Often HTTP 400 for user input, with endpoint-specific behavior |
| Missing MongoDB record | HTTP 404 in history/PDF/graph lookup paths |
| Startup dependency issue | Logs degraded state; readiness is based on Groq client/key rather than all databases |

Exact status codes vary by route; see
[02. API Endpoint Documentation](./02.%20API%20ENDPOINT%20DOCUMENTATION.md).

## Internal exceptions

`app/core/exceptions.py` defines `LLMError`, `EmbeddingError`,
`VectorSearchError`, and `GraphError`. Retrieval and route code catches these
at different boundaries. For example, `run_vector_pipeline()` returns an
empty list on `VectorSearchError`; the main route maps generation failure to
502; embedding failures in some comparison/timeline paths are also surfaced
as 502.

## Graceful degradation patterns

- Planner exceptions log a warning and construct a keyword fallback plan.
- ArXiv source results come directly from the public XML feed.
- Several providers return `[]` or `None` after logging, allowing partial
  evidence from other providers to continue.
- Optional Neo4j/Supabase initialization is skipped when frozen; otherwise
  connection failures leave the process in degraded mode.
- Empty evidence in standard research yields a no-evidence answer rather than
  a model-generated speculative answer.
- Verification failures produce a warning/`SKIPPED` metadata instead of
  failing the whole answer.

These policies favor availability, but an empty result may represent no
matches, unavailable service, disabled integration, or a handled exception.
The response does not always distinguish these cases.

## Logging and observability

`app.config` configures INFO-level logging to stdout and, except on Vercel, a
local `.logs/app.log`. The code logs request IDs, route, latency, selected
model, provider warnings, and startup dependency status. Some provider/error
strings can contain external response content; verify logs do not include
credentials or sensitive user data.

The main health endpoints expose different semantics:

- `/api/health` is liveness-style.
- `/api/ready` tests `pool._ready`, which is set from Groq client/key presence.
- `/api/health/full` performs deeper dependency checks and may report partial
  health.

Do not treat `/api/ready` as proof that MongoDB-backed auth/history works.

## Reliability risks in the current design

1. **Empty-result ambiguity:** broad exception-to-empty fallbacks make a
   successful zero-result search indistinguishable from some provider
   outages without logs.
2. **Readiness mismatch:** MongoDB may be unavailable while Groq-based
   readiness reports ready.
3. **Request budget contention:** provider fan-out, PDF reads, generation,
   coverage checking, and verification share one endpoint timeout.
4. **Process-local state:** rate limits and caches reset on restart and do not
   coordinate across workers.
5. **No durable job queue:** bulk requests run inline; timeout/client
   disconnect can terminate work without a resumable job record.
6. **Optional data dependencies:** default frozen retrieval means external
   provider availability is especially important to source coverage.
7. **Third-party API changes:** response parsing and rate limits are
   connector-specific and may break independently.
8. **Database migrations:** collection/table changes are not tracked by a
   migration framework in the inspected source.

## Operational recovery guidance

- Check `/api/health/full` and logs before changing feature flags.
- Confirm MongoDB reachability separately from Groq readiness.
- Verify provider credentials and rate limits without printing secret values.
- Keep `FREEZE_RETRIEVAL=true` until Supabase RPCs, Neo4j schema, and access
  controls are validated.
- Use a targeted known research query and inspect returned evidence arrays,
  not only the rendered answer.
- If an endpoint times out, examine provider-stage timing and narrow source
  calls before increasing the global timeout.

## Testing reliability claims

Unit and mocked integration tests cover helper behavior and API flows, but
they do not guarantee live provider availability or production reliability.
Connectivity/manual scripts require configured services. See the testing
guide for exact test inventory and CI workflow.
