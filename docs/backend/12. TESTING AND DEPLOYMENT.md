# Testing and Deployment

## Test inventory

The repository contains 35 Python files under `tests/`, plus root-level
manual/debug scripts and `scripts/` evaluation checks.

### Unit tests

`tests/unit/` covers:

- Source record normalization for CORE, OpenAlex, Semantic Scholar, and
  Wikipedia.
- Wikipedia caching.
- Audio hallucination filtering.
- Cache behavior and dependency connectivity checks.
- Credit feature flags and rate limiting.
- Grounded prompt argument propagation.
- Groq response handling, paper relevance, planner fallback, temporary access
  settings, text processing, and upload limits.

### Integration/provider tests

`tests/integration/` includes research grounding, CORE search, Semantic
Scholar enrichment/search, Wikipedia search, and upload endpoints. CI
describes these as HTTP-mocked integration tests; some other root scripts and
connectivity checks may call live external services.

### Root-level/provider scripts

Files such as `test_connectivity.py`, `test_embedding.py`, `test_import.py`,
`test_kaggle.py`, `test_wikipedia.py`, and `test_arxiv_debug.py` are not all
under the main `tests/` tree. Treat these as development/provider checks and
inspect their code/environment requirements before running against live
services. `scripts/eval_retrieval_and_quality.py`,
`scripts/test_quality.py`, and `scripts/test_live_server.py` are also
evaluation or environment-dependent checks rather than the CI unit suite.

## Running tests locally

Typical commands:

```powershell
python -m pytest tests/unit/ -v --tb=short
python -m pytest tests/integration/ -v --tb=short
python -m pytest
ruff check .
ruff format --check .
```

Integration tests import provider modules that may read environment variables
at import time. CI supplies stub CORE/Semantic Scholar values. Live-provider
scripts should not be run without checking their network/API side effects.

## Continuous integration

`.github/workflows/ci.yml` runs on pushes and pull requests to `main` and has
separate jobs for:

1. Ruff lint and format checks on Python 3.11.
2. Mypy on `app/sources/` with third-party import stubs ignored.
3. Environment validation using dummy config values.
4. Unit tests.
5. HTTP-mocked integration tests.

This workflow does not establish a live database/provider deployment test.
The type-check scope is limited to `app/sources/`, not all backend files.

## Continuous deployment

`.github/workflows/cd.yml` runs on pushes to `main` and manual dispatch. It
deploys to Vercel only when the `VERCEL_TOKEN` secret exists; otherwise it
emits a warning and skips. Deployment also expects Vercel organization and
project IDs.

`vercel.json` sends every path to `api/index.py`, which imports the main
FastAPI app and includes frontend assets. It does not encode the README's
described per-route Vercel rewrites.

The optional ArXiv MCP service has its own Dockerfile using Python 3.11 and
exposes port 8000. This Dockerfile is for the MCP server, not the main FastAPI
application.

## Runtime configuration and environment

The project requires Python `>=3.11` according to `pyproject.toml`.
Configuration loads `.env.local` with override, then `.env` without override.
The CI workflow targets Python 3.11; CD currently sets up Python 3.12 for
Vercel. There is no evidence here of a full compatibility matrix across
Python versions.

Core environment variables include MongoDB URI/name, Groq API key(s),
`JWT_SECRET`, `FREEZE_RETRIEVAL`, `CREDIT_SYSTEM_ENABLED`,
`REQUIRE_EMAIL_VERIFICATION`, model names, CORS origins, PDF/audio limits,
and optional Supabase/Neo4j/SMTP/Redis/payment/provider credentials. Use
`python scripts/validate_env.py` to validate expected environment
configuration; inspect that script for deployment-specific requirements.

## Deployment architecture: verified vs unverified

**Verified from repository configuration:**

- Main FastAPI application is exposed through `api/index.py` for Vercel.
- CI has an optional Vercel production deployment job.
- An independent MCP Dockerfile exists.
- README documents a Render option for the primary app.

**Not verified from repository inspection:**

- Whether any production Vercel or Render deployment currently exists/is
  healthy.
- Production environment variable values, worker count, region, scaling, and
  secret configuration.
- Whether a remote MCP service is deployed.
- Whether the deployed service has MongoDB/network access and working
  provider quotas.

## Recommended release checklist

- CI green (Ruff, scoped mypy, environment validation, unit, mocked
  integration).
- Smoke-test `/api/health/full`, signup/login, one research query, one PDF
  upload/read flow, and history ownership using staging dependencies.
- Confirm production `JWT_SECRET`, payment/webhook secrets, SMTP, and database
  credentials are set without printing them.
- Confirm CORS allowlist, trusted proxy/IP settings, and upload limits.
- Keep retrieval frozen until remote schema and RPCs are verified end to end.
- Review logs for secrets/PII; verify alerts and backups.
- Verify deployed endpoints directly after CD; a green deployment job alone
  does not prove all third-party dependencies are healthy.
