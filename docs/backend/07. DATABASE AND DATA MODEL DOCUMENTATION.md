# Database and Data Model Documentation

## Database/client inventory

| Store/client | Main purpose | Runtime status |
|---|---|---|
| MongoDB | Users, payment records, chat history, uploaded PDF text | Initialized regardless of retrieval freeze; account/history/PDF operations depend on it |
| Supabase | Paper metadata/chunks and vector/hybrid search RPC | Skipped when `FREEZE_RETRIEVAL=true` |
| Neo4j | Paper/author/venue/topic graph traversal | Skipped when `FREEZE_RETRIEVAL=true` |
| Upstash Redis | Optional PDF chunk and embedding cache | Initialized only when both URL and token are configured |
| In-memory dictionaries | LLM/plan/API/embed/graph/relations caches and rate limiting | Per-process; used in all configurations |

Database client startup and shutdown are coordinated by `Pool.init()` and
`Pool.close()` in [`app/clients/pool.py`](../../app/clients/pool.py#L326).

## MongoDB collections and observed fields

The database name defaults to `aether_research_assistant`; the URI and
database name are configurable. The repository does not contain a MongoDB
schema migration or JSON Schema validator. The field inventory below reflects
observed writes/queries, not an exhaustive production schema.

### `users`

Created on signup with:

| Field | Source/meaning |
|---|---|
| `_id` | UUID string |
| `email` | Trimmed/lowercase email; unique index created at startup |
| `password_hash` | bcrypt hash |
| `user_metadata` | `full_name`, `institution`, `role` |
| `plan` | Initially `"free"`; payment/webhook handlers can set `"pro"` |
| `credits_used`, `credits_reset_at` | Used when credit enforcement is enabled |
| `stripe_customer_id`, `stripe_subscription_id` | Initialized `None`; updated by payment event paths |
| `is_verified` | Initially opposite of `REQUIRE_EMAIL_VERIFICATION` |
| `created_at`, `updated_at` | UTC timestamps |
| verification/reset token fields | Written only when corresponding flows are enabled/requested; expiry fields are also used |

Other routes update profile metadata, password hash, plan, and credit count.

### `payments`

Payment records contain user/payment/order IDs, amount, currency, status, and
timestamps according to the handler writes. Startup creates a non-unique
`user_id` index and unique `razorpay_payment_id` index. Exact optional fields
depend on payment path.

### `chat_sessions`

History endpoints explicitly insert a session ID, user ID, title, messages,
and timestamps; updates are scoped by both session ID and owner ID. List
queries sort by `updated_at`. The code uses raw JSON body parsing rather than
a dedicated Pydantic history model.

### `uploaded_pdfs`

Upload inserts `_id` (`pdf-<uuid>`), original name, extracted text,
truncation flag, and creation timestamp. This can store large extracted text,
truncated to an internal character cap. The visible record does not include
the uploading user ID.

### MongoDB indexes and readiness

Startup pings MongoDB and creates:

- Unique `users.email`.
- Non-unique `payments.user_id`.
- Unique `payments.razorpay_payment_id`.

If MongoDB initialization fails, the pool records `mongodb_ok=False` and logs
the failure; `_ready` is still calculated from Groq client/key presence.
Consequently readiness does not guarantee database-backed routes will work.

## Supabase tables and RPCs

Application code uses:

- `papers` for a lightweight startup connectivity query (`select("id")`).
- `paper_chunks` as suggested by ingestion scripts and chunk search.
- RPC `match_paper_chunks` with `query_embedding`, `match_threshold`,
  `match_count`, and `filter_ids`.
- RPC `hybrid_search` with `query_text`, `query_embedding`, `match_count`,
  and `filter_ids`.

The offline ingestion scripts also upsert `papers` and `paper_chunks`, using
paper IDs, chunk text/index, embedding, section, and token count. They imply
schema fields; they do not prove the live Supabase schema or RPC definitions.
Those are **unverified** and should be confirmed from the Supabase project
before enabling retrieval.

## Neo4j model

The main graph adapter refers to `Publication`, `Author`, `Venue`, and `Topic`
entities connected by relationships including `CITES`, `WRITTEN_BY`,
`PUBLISHED_IN`, `HAS_TOPIC`, and `SIMILAR_TO`.

The separate `knowledge_graph/schema_and_seed.py` creates uniqueness
constraints for publication ID, author name, venue name, and topic name, plus
a publication-title index. Its sample graph contains five papers and is for
the standalone graph service. No statement here establishes that a production
Neo4j database has those nodes or constraints.

## Cache data and scope

`pool.CACHE` holds bucket dictionaries for `graph`, `embed`, `llm`, `plan`,
`relations`, and `api`; each stores a value and creation timestamp. Most
buckets use `CACHE_TTL` (default 300 seconds); API cache entries use 43,200
seconds. Entries are evicted by removing the oldest item when the configured
maximum is reached. The key is MD5 of joined input arguments; selected
user-dependent buckets include a user ID prefix.

PDF chunk/embedding cache can use Upstash Redis, with in-memory chunk and
embedding maps as fallback. Cache values are not persisted across process
restart unless Redis is active.

## Data ownership and lifecycle caveats

- History records are filtered by authenticated `user_id`.
- User/payment records are associated through user IDs.
- Uploaded PDF records are retrievable by ID and the shown schema has no
  owner field; application-level ownership is not established by this code.
- There is no visible TTL/retention job for accounts, history, PDFs, or
  payment records.
- No migration/versioning framework is visible for MongoDB or Supabase.
- Avoid assuming data retention, backups, tenant isolation, or production
  indexes beyond the explicit startup behavior above.

## Offline ingestion tools

`ingestion/ingestIntoSupabase.py` reads a DBLP-style CSV, cleans text,
generates chunks/embeddings, retries Supabase upserts, and persists a row
checkpoint. `ingestion/scripttouploadpaperchunkstable.py` reads precomputed
chunk embeddings, validates IDs/dimensions, and inserts batches. They are
manual scripts, not startup jobs. Their input file paths, checkpoints, and
remote schema need to be supplied/verified before execution. Do not copy
credential values from those scripts into documentation or logs.
