## Project and architecture

### Tell me about Aether.

Aether is a research assistant with a FastAPI backend. A request is classified
by a query planner, research sources are queried, and a Groq model synthesizes
an answer with citations and source metadata. It also has signup/login,
history, PDF upload and question-answering, dataset/repository discovery, and
audio transcription.

### What problem does it solve?

It aims to reduce the effort required to discover academic papers and
understand a topic by combining source lookup with conversational synthesis.
The backend returns evidence objects alongside the answer so clients can
display papers and datasets. It does not guarantee completeness or factual
correctness.

### Who are the intended users?

Students, researchers, and users exploring technical/scientific literature.
That is the product intent; there is no user-research study in the source
that validates a specific market segment.

### What are its major features?

Research Q&A, planner-routed queries, academic-source search, paper
comparison, timeline/survey routes, chat follow-ups, paper PDF analysis,
dataset/code metadata, login/profile/history, audio transcription, and
optional graph/vector retrieval.

### What makes it different from a general chatbot?

It has explicit research-source connectors, route-specific retrieval and
prompts, citation/source metadata, optional graph/vector layers, and a
no-evidence branch. Those are implementation differences, not proof that its
answers are more accurate than another product.

### Why use RAG?

RAG allows the application to provide current/relevant paper metadata and
document passages as context to the model rather than relying only on
parametric model knowledge. Aether also supports explicit PDF analysis. In
the current default config, Supabase/Neo4j retrieval is frozen, so the active
answer path relies more heavily on external APIs and user-provided documents
until those stores are re-enabled.

### What is the role of AI?

Groq-hosted chat models classify a research plan, draft route-specific
answers, optionally check requirement coverage, verify claims against
retrieved material, and transcribe uploaded audio through Whisper. BGE
embeddings are used for semantic document retrieval; the default freeze flag
returns zero vectors for normal retrieval embedding calls.

### What was the most technically challenging part?

A strong source-backed answer is: coordinating provider-specific retrieval,
query planning, evidence formatting, citation cleanup, and model generation
while handling partial provider failures and keeping responses grounded.

## Technical decisions

### Is this microservices architecture?

No. The backend is a modular monolith: one FastAPI app contains route,
retrieval, integration, and persistence modules. A standalone graph API can
run separately, but that does not make the main system a fully decomposed
microservices architecture.

### Why did you choose this architecture?

The codebase uses one application process to keep development and request
orchestration straightforward. The boundaries are Python modules rather than
independently deployed services. This is a source-grounded description, not a
verified record of the original design rationale.

### How do services communicate?

Inside the main app, Python functions call other modules directly. The
application uses HTTP for Groq and external research APIs, including the
public ArXiv XML API, MongoDB's driver for persistence, Neo4j's driver for
graph queries, and Supabase RPCs for vector search.

### What is an API Gateway in this project?

There is no separately identified API Gateway service in the repository.
FastAPI is the main HTTP entry point and handles route matching/CORS; a
reverse proxy or hosting platform may sit in front of it depending on
deployment.

### How does service discovery work?

The main app does not show dynamic service discovery. External service
addresses and credentials come from environment configuration; Vercel routes
requests to `api/index.py`. Provider URLs are fixed/configured by their
connectors.

### How are communication failures handled?

It depends on the integration. ArXiv uses its XML API directly; planner
failure falls back to keyword extraction; some provider errors are logged and
converted to empty results; core model-generation failures return 502.
Top-level research/chat timeouts return 504. This allows partial availability
but can make an empty result ambiguous.

### How is authentication handled?

MongoDB stores users with bcrypt password hashes. Login returns an HS256 JWT;
protected handlers validate the token and re-load the user. Authentication is
route-level rather than global. Research/chat/media are generally usable
without a token, with optional user context.

### How do you deploy it?

The main app has a Vercel Python entry point (`api/index.py`) and a GitHub
Actions workflow that conditionally deploys to Vercel when secrets exist.
README also describes Render. The repository alone does not establish that a
production deployment is currently live.

### What are the disadvantages of microservices here?

Splitting the current orchestration could add network failure modes,
deployment/configuration complexity, distributed tracing needs, and data
consistency concerns. It may be worthwhile only if independent scaling,
ownership, or release cadence justifies that overhead.

### How would you split Aether if it needed to scale independently?

Start by extracting provider ingestion/search behind a stable internal API,
then separate document processing/embedding as a queued worker, followed by
account/billing only if it has separate operational requirements. Keep the
planner/orchestrator as a clear API boundary initially; define contracts,
timeouts, retries, idempotency, tracing, and ownership before physically
splitting services. Do not split purely by directory name.

## Reliability and limitations

### What happens if no relevant research is found?

The main research route returns a fixed response saying it could not retrieve
sources and will not produce a grounded answer. The response has empty source
arrays and a warning. This branch is taken when all configured evidence
sources, including PDF context, are empty.

### What are the limitations?

- Supabase and Neo4j retrieval are paused by default.
- External providers have their own coverage, latency, rate limits, and
  availability.
- Some provider failures are converted to empty results.
- Citation/verification checks are heuristic and LLM-assisted, not formal
  proof.
- The default JWT secret is unsafe unless overridden.
- Rate limit/cache state is per process.
- PDF records do not visibly have user ownership checks.
- Tests do not establish production deployment health or live-provider
  quality.

### What would you improve with another month?

First, harden auth/config/file access and rotate any source-embedded
credential. Next, add structured provider error states and stage-level
metrics, validate the frozen database schema/RPCs, and run a measurable
retrieval/answer evaluation set. Then add user ownership to PDF storage,
distributed rate limiting, robust webhook idempotency, and deployment smoke
tests.

## Interview framing tips

- Say “modular monolith” for the main app; mention optional independent
  services precisely.
- Distinguish implemented integrations from currently active ones.
- State that “frozen retrieval” disables default vector/graph database
  retrieval, but external providers/PDF flows can still run.
- Do not claim production is deployed solely because a deployment workflow
  exists.
- Present reliability fixes as measured only when you can cite the test or
  result that demonstrates them.
