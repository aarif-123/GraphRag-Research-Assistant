# Authentication and Security

This section documents security-relevant behavior visible in source. It is
not a penetration test or a certification of production security.

## Authentication mechanism

- Accounts are stored in MongoDB.
- Signup hashes passwords with bcrypt; login checks the bcrypt hash.
- JWTs use HS256, include `sub`, `email`, and `exp`, and default to a
  one-week expiration (`JWT_EXPIRY_HOURS`).
- Protected routes parse `Authorization: Bearer ...`, decode the token, and
  look up the user in MongoDB.
- Research, chat, media, and most graph routes do not require a valid token;
  they optionally set user context. Auth/profile/history/payment verification
  endpoints require a token as listed in the API guide.
- Email verification is disabled by default; when enabled, verification codes
  are stored with expiration in MongoDB and delivered by SMTP or log-only
  fallback.

## Plan gates and rate limits

- Credit enforcement defaults off. When enabled, free-user daily credit
  counters are stored in MongoDB; Pro users bypass credits.
- Pro-only feature gates remain active for survey, bulk research, and
  `/v1/chat/completions`.
- Rate limiting defaults to 30 requests per minute and uses in-memory
  timestamps keyed by client IP. It is not distributed across workers,
  instances, or deployments.
- Trust of proxy-forwarded client IP headers is not established in the helper;
  verify the ASGI/server/proxy configuration before relying on IP limiting.

## Input and file handling

- Pydantic validates many request bodies, including query length, enum/range
  style parameters, and file-related model values.
- PDF upload checks `.pdf` filename extension, content length/actual bytes,
  and extracted text. It does not visibly perform malware scanning or bind
  uploaded documents to an account.
- PDF download and parser paths enforce byte limits for remote files, but
  URL fetching should still be reviewed for SSRF policy, redirect handling,
  and allowed host controls before public deployment.
- Audio uploads are size-limited and sent to Groq Whisper.
- External URLs and model output are cleaned for citation links and secret
  patterns, but output cleanup is not a general HTML sanitizer.

## Sensitive configuration

`JWT_SECRET` has a development fallback in `app/config.py`; production must
set a long, random secret and reject the default. Provider API keys, database
URIs, SMTP credentials, payment keys, and webhook secrets belong in a
secret manager/environment variables, not source control.

An ingestion script contains hard-coded remote Supabase configuration. The
value is omitted from this guide. If it is a real key, consider it exposed:
rotate/revoke it, remove it from source and history where feasible, and
replace it with an environment-sourced secret. The script is offline tooling,
but exposure still affects the Supabase project.

## Specific security-relevant implementation caveats

1. **PDF access control:** upload records do not show an owner ID, and
   `GET /api/pdf/{pdf_id}` fetches by ID without a visible ownership check.
   Treat these IDs as bearer-like references unless application authorization
   is added and verified.
2. **Weak password minimum:** six characters is the current minimum; no
   stronger password policy or MFA is visible.
3. **Account/password endpoints:** `PUT /api/auth/password` requires a
   logged-in JWT but the request model does not require the current password.
4. **Verification/reset codes:** code generation uses `random.randint` for a
   six-digit numeric code; brute-force protections/attempt counters are not
   visible in those endpoints.
5. **Mock email:** when SMTP credentials are absent, verification/reset
   contents are logged. Do not enable verification/reset in a shared or
   production environment with this fallback.
6. **Default JWT secret:** the code default is unsuitable for production; a
   missing environment variable can leave this weak setting active.
7. **Payment endpoints:** Razorpay order creation has no visible JWT
   requirement; webhook signature validation depends on configuration.
   Review caller identity, amount validation, webhook idempotency, and
   deployment secrets before production.
8. **Database availability vs readiness:** `_ready` depends on Groq client
   and key configuration, not MongoDB health. A ready response can coexist
   with unavailable user/database endpoints.
9. **CORS:** default origins include `"*"`, while credentials are disabled.
   Configure an explicit production allowlist.
10. **Logs and error detail:** exceptions are logged and some provider
    exceptions are returned in HTTP error details; ensure secrets, personal
    data, or sensitive provider response bodies are not emitted.

These are source observations and follow-up areas, not findings from an
authorized security test. Do not expose real values in documentation or
commit history.

## Payment/webhook verification

Razorpay verification computes the expected HMAC signature with the configured
secret and compares it before changing the user plan. Stripe webhook code
checks the signature only when `STRIPE_WEBHOOK_SECRET` is configured. Webhook
replay/idempotency and event coverage should be tested against provider
contracts before enabling payments.

## Baseline hardening checklist

- Require non-default JWT and provider secrets in production startup validation.
- Restrict CORS origins and configure trusted proxy handling.
- Add ownership checks for uploaded documents.
- Add verification/reset attempt limits and stronger token generation.
- Disable log-only email fallback outside local development.
- Authenticate/authorize order creation and validate amount/currency.
- Add webhook idempotency and verify event signatures are mandatory.
- Ensure PDF fetches cannot access internal/private network addresses.
- Review logging for credential/PII disclosure and set retention policies.
- Keep frozen database behavior explicit; do not enable retrieval until remote
  schema, permissions, and row-level access policies are verified.
