# Async Programming and Performance

## Async model

FastAPI route handlers are primarily `async def`. HTTPX is used for
asynchronous network requests. Synchronous clients and CPU/blocking work are
offloaded using `asyncio.to_thread()` in major paths, including MongoDB
operations, Neo4j queries/connectivity checks, and PDF parsing. Local
SentenceTransformer inference is also run in a worker thread.

The application still contains synchronous libraries (PyMongo, Neo4j,
SentenceTransformer, PyMuPDF). A path that invokes them directly on the event
loop could block other requests; inspect any new call site and follow the
existing thread-offload pattern where appropriate.

## External provider fan-out

Research and chat workflows use `asyncio.gather()` to run independent graph,
vector, ArXiv, Semantic Scholar, CORE, and enrichment requests concurrently.
Some gather calls use `return_exceptions=True` and convert individual failures
to empty results; others allow the failure to propagate. The exact fallback is
route-specific.

For high-depth named-source questions, up to three primary PDFs are fetched
concurrently. Bulk research uses a semaphore capped at three concurrent
queries.

## Timeouts and connection limits

| Work | Source configuration |
|---|---|
| Main research/chat endpoint | `REQUEST_TIMEOUT`, default 60 seconds |
| Groq shared HTTP client | `GROQ_TIMEOUT`, default 30 seconds; connect timeout 5 seconds |
| Shared Groq client pool | Max 30 connections, max 15 keepalive connections |
| Hugging Face embedding request | `EMBED_TIMEOUT`, default 20 seconds; connect 5 seconds |
| ArXiv XML request | HTTPX timeout of 8 seconds |
| Remote PDF parse download | 60-second timeout and configured size limit |
| Neo4j connect check | `asyncio.wait_for()` around worker-thread call, 10 seconds |
| Audio transcription | Explicit request timeout of 60 seconds |

These settings can interact: a sequence of individually bounded provider
calls, PDF downloads, model generation, and verification may approach or
exceed the top-level request timeout.

## Caching

The in-process cache has configurable size (default 512) and TTL (default
300s), except API results use 12 hours. It caches embedding, LLM, plan, graph,
relation, and API responses. Temperature-zero LLM calls can be reused.
Selected buckets are prefixed with current user ID.

Potential implications:

- Cache state is local to one process/worker; no cross-process coherence.
- User scoping is applied only to selected buckets, not uniformly.
- Cache mutation and LRU eviction are not protected by a global lock.
- MD5 is used as a cache key digest; it is not used as an authentication
  primitive.
- PDF content caching can use Upstash Redis when configured; its fallback
  dictionaries are local memory.

## Embeddings and CPU cost

`app/clients/groq.py` tries to load `BAAI/bge-base-en` locally at import time
with CPU device. If missing/unavailable, it attempts Hugging Face inference
when embedding is requested. Batch creation caches per-input results and can
fall back from local to remote. Startup cost, model download availability,
CPU latency, memory use, and HF quotas affect performance.

With retrieval frozen, ordinary `create_embedding()` calls return zero
vectors immediately. PDF-related calls explicitly bypass that behavior so
local uploaded-paper search can still use embeddings. Verify `bypass_freeze`
is only used for intended document-local flows.

## Rate limiting and scaling

The rate limit store keeps per-IP timestamps in process memory and cleans
stale entries every five minutes. It is not shared across worker processes
and does not provide a cluster-wide cap. Uvicorn `WORKERS` can therefore
multiply the effective limit and duplicate caches.

Scaling the API horizontally also multiplies:

- Groq and external-provider concurrency.
- In-memory cache copies.
- Per-process rate-limit capacity.
- Local embedding model memory/CPU usage.

An external cache/rate limiter or a centrally enforced gateway limit would be
needed for consistent multi-instance behavior.

## Performance observability

Research responses include `latency_ms`; logs also include request IDs,
selected planner route/model, verification timing, and provider warnings.
No metrics exporter, tracing SDK, benchmark dashboard, or production
performance SLO is established by the inspected code/configuration.

## Practical optimization areas

- Measure endpoint stage timings (planner, retrieval by provider, prompt,
  generation, verification) before tuning.
- Avoid loading duplicate embedding models per worker where memory is tight.
- Add provider-specific semaphores/timeouts and retain partial results.
- Store normalized metadata once rather than repeatedly enriching candidates.
- Consider request coalescing for duplicate provider/API calls.
- Use a distributed rate limiter/cache when deployed with multiple workers.
- Keep PDF parsing, model execution, and synchronous database operations off
  the event loop.
