# Query Planner Deep Dive

## Purpose and call site

`plan_query(query, context="")` in
[`app/core/planner.py`](../../app/core/planner.py#L237) converts natural
language and recent conversation into a `QueryPlan`. The main research and
chat flows use the plan to choose retrieval and answer styles. The planner is
an LLM call to `PLAN_MODEL`, not a deterministic symbolic parser.

Before calling the model, it checks the in-process `"plan"` cache using a key
derived from `plan_v2`, the raw query, and the first 200 characters of context.
The `v2` prefix prevents earlier plans missing newer fields from being reused.

## Plan fields

`QueryPlan` in [`app/models/research.py`](../../app/models/research.py#L55)
contains:

| Field | Meaning |
|---|---|
| `standalone_query` | Rewritten/self-contained query, useful for follow-ups |
| `route` | One of ten supported route labels |
| `graph_anchors` | Up to three entities/paper-title fragments for graph lookup |
| `vector_keywords` | Up to five dense semantic terms |
| `required_metrics` | Up to ten facts/metrics the user requested |
| `reasoning_path` | One-sentence retrieval/synthesis plan |
| `ambiguous` | Whether the follow-up could not be resolved |
| `cache_key_str` | Planner-supplied or locally derived query key |
| `raw` | Original parsed plan object |
| `named_entities` | Named paper/method/dataset/concept records |
| `search_tiers` | Up to seven exact phrase searches |
| `depth` | `standard` or `high` |
| `requirements` | Up to ten answer-coverage checklist entries |

## Route taxonomy in implementation

The prompt describes these ten values; the parser accepts the same set:

| Route | Typical intent | Expected behavior |
|---|---|---|
| `entity_lookup` | Paper author, year, venue, or other fact | Direct metadata lookup |
| `structured` | List/filter papers | Structured paper listing |
| `title_lookup` | Record for one specifically named paper | Title-focused lookup |
| `compare` | Compare multiple papers/methods | Comparison prompt |
| `timeline` | Research evolution over time | Chronological prompt |
| `survey` | Broad state-of-field synthesis | Survey prompt; heavy model |
| `conceptual` | General explanation/tutoring | Conceptual prompt |
| `rag` | Specific concept/paper explanation | Grounded evidence prompt |
| `chitchat` | Greeting/non-research | No research retrieval |
| `context_only` | Follow-up based on prior response | Conversation-context response |

The long system prompt has a stale “one of the 9 routes” phrase even though
the actual route list and validation set both contain ten.

## LLM planning prompt

The strategic prompt asks the model to:

1. Resolve pronouns from up to the last three conversation turns.
2. Choose exactly one route.
3. Identify named research entities and whether primary sources are needed.
4. Produce ordered search tiers, including exact-title searches for named
   papers when relevant.
5. Extract minimal graph anchors and semantic keywords.
6. List required metrics.
7. Classify answer depth and, for high depth, create answer requirements.
8. State a reasoning path and normalized cache key.

`PLAN_QUERY_TEMPLATE` is the current compact template used by `plan_query()`.
The larger `SUPER_MASTER_PROMPT` documents expanded rules/examples but is not
the template assembled in the active call shown in the implementation.

## Parsing and sanitization

`_parse_planner_response()` accepts direct JSON, JSON wrapped in Markdown
fences, or JSON extracted from surrounding text. It requires a JSON object.
On exceptions, `plan_query()` logs a warning and uses `_fallback_plan_data()`.

The planner then:

- Limits and filters string lists (anchors 3, keywords 5, metrics 10, tiers
  7, requirements 10).
- Keeps named entities only when they are dictionaries with non-empty string
  names.
- Restricts `depth` to `standard` or `high`.
- Restricts route to the ten allowed values; invalid route becomes `rag`.
- Uses the original query if `standalone_query` is missing/empty.
- Builds a `QueryPlan` and caches it.

The fallback extracts up to eight distinct lowercase query words after a
small stop-word filter, uses them as vector keywords, chooses route `rag`,
and builds one search tier. It does not infer a sophisticated route or
primary-source entity data.

## Retrieval fields in practice

- `graph_anchors` are used for graph-focused lookup/structured routes.
- `vector_keywords` or `standalone_query` guide database and external
  research retrieval, depending on endpoint.
- `search_tiers` prioritize exact title/entity searches before supporting
  terms in named entity paths.
- `required_metrics` guide retrieval and the primary source passage query.
- `named_entities` with `primary_source_required=true` enable PDF passage
  extraction only on high-depth `rag` and `compare`.

Route-specific wiring is not identical for every endpoint; timeline, survey,
chat, compare, and the main research route have separate implementations.

## Depth-aware answer checks

For a high-depth plan, the research route:

1. Fetches full text from up to three identified papers (if URLs exist).
2. Selects up to six overlapping passages per paper, each limited to
   approximately 800 characters.
3. Passes `depth`, `requirements`, and title-labelled primary passages into
   `grounded_prompt()`.
4. Increases answer `max_tokens` from 3,500 to 4,500.
5. Calls `check_requirements_covered()` after generation and appends an
   evidence-gap warning for missing requirements.

This second planner-model call checks whether an answer appears to address a
checklist; it does not fetch missing evidence or revise the answer.

## Failure modes and observability

- Planner/API/model failures produce a warning log and deterministic fallback
  plan instead of aborting research.
- Invalid JSON can be recovered only if a JSON object can be extracted from
  the response text.
- A syntactically valid but low-quality planner response can still route to an
  imperfect path; sanitization validates shape and enum values, not factual
  correctness.
- Plan cache is process-local and has no cross-worker consistency.
- Logs include selected route, anchors, keywords, tiers, and depth; avoid
  logging secrets in provider errors or prompts.
